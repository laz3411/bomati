## 발표 방향

- 대상: 코딩 경험이 있는 고등학생 심사위원
- 톤: 쉬운 문제 제기 + 구현 가능한 수준의 기술 설명
- 핵심 메시지: 버마티는 승객의 위치와 버스 운행 정보를 이용해, 필요한 순간에 하차벨을 자동으로 알려 주는 스마트 하차 보조 시스템이다.
- 주의: 실제 상용 버스 연동이 완료되지 않았다면 “실제 적용”이라고 단정하지 않고 “실제 적용을 위한 설계” 또는 “프로토타입 구현”으로 표현한다.

### 발표자 멘트

버마티는 버스에서 내릴 때의 불편함을 해결하기 위해 만든 스마트 하차 보조 시스템입니다. 사용자의 목적지를 기준으로 하차 시점을 알려 주고, 필요하다면 앱에서 하차벨 요청까지 전달하는 것을 목표로 합니다.

## 2. 문제 정의: 왜 필요한가?

### 화면용 문구

버스 하차에는 생각보다 많은 불편이 있습니다.

- 버스가 혼잡하면 하차벨까지 이동하기 어렵다.
- 초행길에서는 정류장을 지나칠까 봐 계속 노선을 확인해야 한다.
- 안내방송을 놓치거나 주변 소음 때문에 하차 시점을 판단하기 어렵다.
- 고령자, 어린이, 장애인 등 교통약자에게는 이 문제가 더 크게 느껴진다.

### 핵심 문장

버마티는 “어디서 내려야 하는지”와 “언제 하차벨을 눌러야 하는지”를 한 번에 보조한다.

## 3. 사용 흐름과 기대 효과

### 화면용 문구

1. 사용자가 버스 노선과 목적지 정류장을 선택한다.
2. 탑승한 버스를 기준으로 하차 알림을 예약한다.
3. GPS와 버스 운행 정보를 이용해 현재 위치를 확인한다.
4. 하차 시점이 가까워지면 알림을 제공한다.
5. 사용자가 직접 누르기 어려운 상황에서는 앱에서 하차 요청을 전송한다.

### 기대 효과

- 하차벨까지 이동하기 어려운 상황의 불편 감소
- 정류장 통과에 대한 불안과 긴장 완화
- 초행길에서도 하차 시점을 놓칠 가능성 감소
- 교통약자의 대중교통 이용 접근성 향상

### 표현 수정

“노선 확인이 필요 없다”보다는 “노선과 현재 위치를 계속 확인해야 하는 부담을 줄인다”가 정확하다.

## 5. Roblox 프로토타입 구현

### 제목

Roblox 안에서 기능을 어떻게 검증했는가?

### 화면용 문구

Roblox는 실제 버스 환경을 그대로 재현하기보다, 핵심 로직을 빠르게 검증하기 위한 시뮬레이션 플랫폼으로 사용했다.

- 버스가 정류장 사이를 이동하는 가상 환경 구성
- 승객의 목적지 선택 및 하차 예약 구현
- 목적지 접근 시 알림을 발생시키는 조건문 구현
- 하차벨 버튼 입력에 따라 버스 오브젝트의 상태 변경
- 승객이 버스에서 내리면 예약 상태를 해제하는 로직 구현

### 구현 논리 예시

`현재 정류장 == 목적지 정류장` 또는 `목적지까지 남은 거리 <= 기준 거리`이면 하차 알림을 발생시킨다.

실제 서비스에서는 이 조건을 GPS, 지도 데이터, 버스 도착 정보 API로 대체할 수 있다.

## 6. 시스템 구조

### 구성 요소

#### Roblox 체험 서버

가상 버스의 이동, 정류장, 승객 상태를 관리한다. 실제 앱과 버스 시스템의 동작을 테스트하는 시뮬레이션 영역이다.

#### 웹 앱 / APK

사용자가 노선과 목적지를 선택하고, 하차 예약 및 하차벨 요청을 수행하는 사용자 인터페이스다.

#### Firebase

사용자 세션, 하차 예약 정보, 요청 상태를 저장하고 각 클라이언트에 전달하는 백엔드 역할을 한다.

#### 브릿지 PC

인터넷으로 전달된 하차벨 요청을 실제 하드웨어 신호로 변환하는 중계 장치다. 서버와 마이크로컨트롤러 사이의 프로토콜 변환을 담당한다.

#### 실제 하차벨

마이크로컨트롤러가 릴레이 또는 트랜지스터 회로를 통해 작동시키는 물리 장치다. 실제 차량에 적용할 때는 차량 전기 시스템과 안전 규격을 반드시 검토해야 한다.

### 데이터 흐름

웹 앱/APK → Firebase → 브릿지 PC → 마이크로컨트롤러 → 하차벨

Roblox 프로토타입은 이 흐름을 가상 환경에서 재현해 기능과 상태 변화를 검증한다.

## 7. 사용 기술

### 화면용 문구

- Roblox Studio / Lua: 가상 버스, 정류장, 버튼, 이동 로직 구현
- 웹 앱 또는 APK: 노선 선택, 목적지 설정, 알림 및 요청 UI 구현
- Firebase: 인증, 실시간 데이터베이스, 요청 상태 동기화
- REST API 또는 실시간 데이터 연동: 버스 위치와 정류장 정보 전달
- Pico 2W: Wi-Fi 통신과 하드웨어 제어
- 브릿지 프로그램: 서버 메시지를 하차벨 제어 신호로 변환

### 기술적으로 중요한 점

하차벨 요청은 단순히 버튼을 한 번 누르는 이벤트가 아니라, “예약됨 → 요청 전송 → 수신 확인 → 작동 완료 → 종료”라는 상태를 가져야 한다. 이 상태 관리가 있어야 중복 요청과 통신 실패를 처리할 수 있다.

## 9. 실제 적용을 위한 설계

### 제목

실제 버스에 적용한다면?

### 화면용 문구

실제 서비스에서는 사용자의 GPS 위치와 버스 운행 데이터를 결합한다.

- GPS로 사용자의 현재 위치를 확인한다.
- 버스 API 또는 BIS API에서 노선·정류장·도착 정보를 받는다.
- 목적지 정류장까지의 거리와 예상 정차 순서를 계산한다.
- 임계 거리 또는 다음 정류장 정보를 기준으로 하차 알림을 제공한다.
- 버스 탑승 여부가 불확실할 때는 사용자 확인 절차를 둔다.

### 하차 판단 방법

GPS만으로는 터널, 고층 건물, 위치 오차 때문에 정확도가 떨어질 수 있다. 따라서 GPS 위치 하나만 사용하기보다 다음 정보를 함께 활용하는 것이 안정적이다.

- 사용자 위치와 버스 노선의 공간적 일치
- 버스의 이동 방향과 속도
- 정류장 도착·출발 이벤트
- 블루투스 비콘 또는 차량 내 통신 신호
- 사용자의 탑승 확인 및 앱 상태

하차 후에는 사용자의 위치가 버스의 이동 경로와 분리되는지, 또는 하차 확인 버튼이 눌렸는지를 기준으로 예약을 종료할 수 있다.

## 심사위원 질문 대비 답변

### Q. Roblox와 실제 버스는 어떻게 연결되나요?

현재 Roblox는 핵심 기능을 검증하는 프로토타입입니다. 실제 구조에서는 Roblox 대신 실제 버스 데이터 API와 앱을 연결하고, 서버의 하차 요청을 브릿지 PC와 마이크로컨트롤러가 받아 하차벨 신호로 변환합니다.

### Q. 사용자가 실제로 버스에 탔다는 것을 어떻게 알 수 있나요?

초기 버전에서는 사용자가 노선과 탑승을 직접 확인합니다. 정확도를 높이려면 GPS의 이동 경로, 버스 위치, 블루투스 비콘, NFC 또는 태그리스 방식 등을 조합할 수 있습니다.

### Q. 사용자가 버스에서 내렸다는 것을 어떻게 판단하나요?

하차 정류장 통과 후 사용자의 위치가 버스 경로와 분리되는지 확인하고, 앱의 하차 확인 입력을 함께 사용합니다. GPS 하나만으로 판단하지 않고 여러 신호를 조합하는 것이 안전합니다.

### Q. 통신이 끊기면 어떻게 되나요?

앱에는 마지막으로 저장된 목적지와 정류장 정보를 보관하고, 통신이 끊긴 동안에는 로컬 알림을 우선 제공합니다. 하차벨 작동은 통신 복구 후 중복 요청이 발생하지 않도록 요청 ID와 완료 상태를 관리해야 합니다.

### Q. 실제 버스에 바로 설치할 수 있나요?

프로토타입 단계에서 바로 설치하는 것은 적절하지 않습니다. 실제 적용 전에는 운수회사와의 협의, 차량 제어 시스템 분석, 전기적 절연, 인증, 장애·오작동 대응 시험이 필요합니다. 현재 프로젝트의 목표는 이 적용을 위한 사용자 경험과 시스템 구조를 검증하는 것입니다.

## 기술 설명 보강본: 발표에서 임팩트 있게 말하는 방법

### 1. 통신 구조

#### 현재 프로토타입에서 설명할 내용

앱과 Roblox, 하드웨어가 같은 이벤트를 공유하도록 Firebase Realtime Database를 중간 상태 저장소로 사용한다. 데이터가 바뀌면 각 클라이언트가 실시간 리스너로 변화를 받아 화면과 장치 상태를 갱신한다.

쉽게 말하면, Firebase는 “하차벨을 눌렀다”라는 사건을 여러 프로그램에 동시에 전달하는 온라인 게시판과 같다.

#### 실제 서비스에서 고려할 통신 방식

- HTTPS/REST API: 노선, 정류장, 사용자 설정처럼 요청-응답이 분명한 데이터
- WebSocket: 하차 요청이나 차량 상태처럼 서버에서 즉시 전달해야 하는 이벤트
- MQTT: 저전력 장치가 작은 메시지를 자주 주고받을 때 적합한 경량 메시징 프로토콜
- Firebase Realtime Database 또는 Firestore: 프로토타입에서 실시간 상태를 빠르게 공유하기 좋음

발표용 결론: “데이터 조회는 HTTPS, 실시간 이벤트는 WebSocket 또는 MQTT처럼 역할에 맞는 프로토콜을 선택한다.”

### 2. 메시지 예시

실제 하차 요청은 단순한 `true/false`보다 다음처럼 고유한 요청 정보가 있는 객체로 관리하는 것이 안전하다.

```json
{
  "requestId": "req_20260915_001",
  "busId": "bus_102",
  "targetStopId": "stop_381",
  "action": "STOP_BUTTON_REQUEST",
  "status": "REQUESTED",
  "createdAt": 1789431926
}
```

각 필드의 의미를 설명하면 다음과 같다.

- `requestId`: 같은 요청이 두 번 실행되지 않게 하는 고유 번호
- `busId`: 어떤 버스에 보낼 요청인지 구분
- `targetStopId`: 목적지 정류장 식별자
- `action`: 하차벨 요청이라는 이벤트 종류
- `status`: 요청의 현재 상태
- `createdAt`: 오래된 요청을 구분하기 위한 생성 시각

### 3. 상태 머신

하차벨 요청은 다음 상태를 순서대로 거친다.

`IDLE → REQUESTED → DELIVERED → ACTUATED → COMPLETED`

- `IDLE`: 요청 없음
- `REQUESTED`: 앱에서 요청 생성
- `DELIVERED`: 브릿지 PC 또는 Pico 2W가 수신
- `ACTUATED`: 하차벨 제어 신호 출력
- `COMPLETED`: 작동 완료 기록

통신이 끊기면 `RETRYING`, 일정 시간 응답이 없으면 `FAILED` 상태를 추가할 수 있다. 이 구조는 “버튼을 눌렀는데 작동했는지 모르는 문제”를 해결한다.

### 4. 라이브러리와 역할

실제 앱 구현 시 사용할 수 있는 기술 스택은 다음과 같이 설명할 수 있다. 단, 아직 사용하지 않은 기술은 “사용했다”가 아니라 “확장 시 적용할 수 있다”고 표현한다.

- `Firebase SDK`: 인증, 실시간 데이터베이스, 이벤트 동기화
- `Google Maps Platform` 또는 공공 지도 API: 지도, 좌표, 정류장 위치
- 지역 교통정보 `BIS API`: 버스 위치와 정류장 도착 정보
- `WebSocket` 라이브러리: 양방향 실시간 이벤트 통신
- `MQTT` 클라이언트: Pico 2W 같은 장치와의 경량 통신
- `Pico 2W MicroPython network/socket`: Wi-Fi 연결과 장치 제어
- Roblox `RemoteEvent`: Roblox 클라이언트와 서버 사이의 이벤트 전달

발표에서 중요한 것은 라이브러리 이름을 많이 말하는 것이 아니라, “각 기술이 어느 문제를 해결하는지”를 연결해서 말하는 것이다.

### 5. GPS만으로 판단하지 않는 이유

GPS는 위치를 알려 주지만, 실내·터널·고층 건물 주변에서는 오차가 커질 수 있다. 따라서 다음 신호를 함께 사용하는 센서 융합 구조가 적절하다.

`GPS 위치 + 버스 GPS + 이동 방향 + 정류장 이벤트 + 사용자 확인`

예를 들어 사용자의 위치가 목적지 정류장 근처이고, 버스가 해당 정류장 방향으로 이동 중이며, 버스 API가 다음 정류장을 목적지로 알려 주면 하차 알림의 신뢰도가 높아진다.

### 6. 보안과 안전성

- Firebase 보안 규칙으로 사용자가 자신의 예약만 읽고 쓰도록 제한
- `requestId`로 중복 하차벨 작동 방지
- 서버에서 허용된 버스와 정류장인지 검증
- 장치가 일정 시간 이상 신호를 내보내지 않도록 자동 타임아웃 적용
- 실제 차량 회로와는 릴레이·옵토커플러 등으로 전기적 절연 검토

한 문장 요약: “스마트 기능일수록 정상 작동보다 오작동을 어떻게 막는지가 더 중요하다.”
