# 버마티(BuMaTi) 신규 PPT 구성 조언

> 이 문서는 기존 PPT의 문구·페이지·디자인을 참고하지 않고, 버마티 프로젝트를 코딩 경험이 있는 고등학생 심사위원에게 설득력 있게 설명하기 위한 새로운 발표 구조를 제안한다.

## 1. 발표의 핵심 전략

발표를 “기능 소개”로 시작하면 평범한 앱 발표처럼 보일 수 있다. 다음 질문에 답하는 순서로 구성하는 것이 좋다.

1. 어떤 불편을 해결하려는가?
2. 기존 방법으로는 왜 충분하지 않은가?
3. 버마티는 어떤 방식으로 해결하는가?
4. 실제로 무엇을 구현했고, 어떻게 검증했는가?
5. 아직 해결하지 못한 문제와 다음 단계는 무엇인가?

핵심 메시지는 한 문장으로 고정한다.

> 버마티는 사용자의 목적지와 이동 상태를 바탕으로 하차 시점을 판단하고, 필요한 경우 하차벨 요청까지 전달하는 대중교통 보조 시스템이다.

## 2. 권장 발표 분량

10~12장의 본 발표 슬라이드와 2~3장의 질문 대비 슬라이드를 권장한다.

- 문제와 사용자: 2장
- 해결 방식과 사용자 흐름: 2장
- 기술 구조: 3장
- 구현 및 검증: 2장
- 한계와 발전 방향: 2장
- 결론: 1장

한 슬라이드에 메시지는 하나만 둔다. 기술을 많이 보여주는 것보다 심사위원이 발표가 끝난 뒤 시스템 구조를 기억하게 하는 것이 중요하다.

## 3. 새로운 슬라이드 구성안

### Slide 1. 한 문장으로 이해되는 표지

#### 목적

첫 5초 안에 서비스가 무엇인지 전달한다.

#### 넣을 내용

제목: `버마티(BuMaTi)`

부제: `내릴 정류장을 놓치지 않도록, 하차 과정을 스마트하게`

하단 한 줄: `위치 정보 + 대중교통 데이터 + 하차벨 제어`

#### 시각 자료

버스 내부, 스마트폰, 목적지 핀, 하차벨이 하나의 흐름으로 이어지는 단순한 이미지.

#### 발표 멘트

“버마티는 버스에서 언제 내려야 하는지 알려 주고, 사용자가 하차벨에 접근하기 어려울 때 하차 요청을 전달하는 시스템입니다.”

---

### Slide 2. 문제를 사용자 상황으로 보여주기

#### 목적

추상적인 “교통 불편”이 아니라 실제 장면을 보여 준다.

#### 구성

세 가지 사용자 상황을 짧게 제시한다.

- 혼잡한 버스에서 하차벨까지 이동하기 어려운 승객
- 초행길이라 정류장을 놓칠까 걱정하는 승객
- 안내방송이나 표지판을 즉시 확인하기 어려운 승객

#### 중요한 표현

“모든 사람이 불편하다”라고 과장하지 않는다.

> 특정 상황에서는 기존 하차 방식이 사용자에게 불필요한 긴장과 행동 부담을 만든다.

#### 시각 자료

복잡한 글 대신 네컷 일러스트 또는 한 장면의 대비 이미지.

---

### Slide 3. 문제를 기술적으로 정의하기

#### 목적

문제 해결의 기준을 명확히 한다.

#### 화면용 문구

버마티가 판단해야 하는 것은 세 가지다.

1. 사용자가 어느 버스에 탑승했는가?
2. 목적지 정류장까지 얼마나 남았는가?
3. 하차 알림 또는 하차 요청을 언제 전달해야 하는가?

#### 판단 기준

`사용자 상태 + 버스 위치 + 목적지 정류장 + 통신 상태`

#### 발표 포인트

이 슬라이드에서 “단순 알람 앱이 아니라 상태를 판단하는 시스템”이라는 인상을 준다.

---

### Slide 4. 해결책을 사용자 흐름으로 설명하기

#### 화면용 흐름

`목적지 선택 → 탑승 확인 → 이동 상태 확인 → 하차 시점 판단 → 알림/하차 요청 → 종료`

각 단계를 한 줄로 설명한다.

- 목적지 선택: 사용자가 내릴 정류장 지정
- 탑승 확인: 노선·차량 또는 사용자의 탑승 상태 연결
- 이동 상태 확인: 위치와 운행 데이터를 주기적으로 확인
- 하차 시점 판단: 목적지 접근 여부 계산
- 알림/요청: 알림을 보여주거나 하차벨 요청 생성
- 종료: 하차 후 예약 상태 해제

#### 시각 자료

가로 방향의 6단계 파이프라인. 화살표를 많이 사용하지 말고, 현재 시스템 상태가 이동하는 것처럼 표현한다.

---

### Slide 5. 시스템 전체 구조를 한 장으로 보여주기

#### 목적

심사위원이 가장 궁금해할 “앱과 실제 하차벨이 어떻게 연결되는가?”를 설명한다.

#### 권장 구조

```text
[사용자 앱]
     ↓ HTTPS / WebSocket
[백엔드·실시간 상태 저장소]
     ↓ MQTT 또는 WebSocket
[브릿지 프로그램]
     ↓ GPIO / 제어 신호
[마이크로컨트롤러]
     ↓
[하차벨]
```

#### 각 요소의 역할

- 사용자 앱: 목적지 설정과 요청 생성
- 백엔드: 예약·요청·완료 상태 저장
- 브릿지: 인터넷 메시지를 장치 명령으로 변환
- 마이크로컨트롤러: 물리적인 출력 신호 제어
- 하차벨: 최종 작동 장치

#### 주의

실제로 구현한 요소와 향후 설계 요소를 색상으로 구분한다.

- 파란색: 현재 구현
- 회색: 시뮬레이션
- 점선: 향후 실제 적용

---

### Slide 6. 통신 방법을 쉽게 설명하기

#### 제목 예시

`데이터의 종류에 따라 통신 방법을 나눈다`

#### 비교표

| 통신 방식 | 적합한 데이터 | 쉬운 설명 |
|---|---|---|
| HTTPS/REST | 노선 조회, 설정 저장 | 요청하면 서버가 답을 주는 방식 |
| WebSocket | 실시간 알림, 상태 변경 | 연결을 유지하며 즉시 주고받는 방식 |
| MQTT | 장치 명령, 센서 메시지 | 작은 메시지를 가볍게 전달하는 방식 |
| Firebase 실시간 기능 | 프로토타입 상태 동기화 | 데이터가 바뀌면 연결된 화면에 바로 알려주는 방식 |

#### 기술적으로 인상적인 한 문장

> 버마티는 모든 통신을 하나의 방식으로 처리하지 않고, 요청-응답 데이터와 실시간 이벤트, 장치 제어 메시지를 분리해 설계한다.

#### 고등학생 심사위원에게 설명하는 비유

- REST: 민원 창구
- WebSocket: 계속 연결된 전화
- MQTT: 짧은 무전 메시지
- 실시간 데이터베이스: 모두가 공유하는 상태판

---

### Slide 7. 핵심 로직: 하차 시점을 어떻게 판단하는가?

#### 목적

서비스의 핵심 알고리즘을 보여준다.

#### 의사코드

```text
if 사용자가_탑승_중이고
   현재_노선이_예약_노선과_일치하고
   목적지까지_남은_정류장 <= 기준값:
       하차_알림_생성

if 사용자가_하차벨_요청을_보냈고
   요청이_중복되지_않고
   통신이_정상이라면:
       하드웨어_제어_명령_전송
```

#### 반드시 설명할 내용

GPS만으로 정류장을 판단하면 위치 오차가 생길 수 있다. 따라서 다음 정보를 함께 사용하는 방향이 더 안정적이다.

`GPS 위치 + 버스 위치 + 이동 방향 + 정류장 이벤트 + 사용자 확인`

#### 발표에서 피할 표현

“AI가 알아서 정확하게 판단한다”라고 말하지 않는다. 현재 구현이 규칙 기반이라면 “조건 기반 상태 판단”이라고 설명한다.

---

### Slide 8. 상태 머신과 오류 처리

#### 목적

단순 데모가 아니라 실제 서비스 관점에서 설계했다는 점을 보여준다.

#### 상태 흐름

```text
IDLE
  ↓
REQUESTED
  ↓
DELIVERED
  ↓
ACTUATED
  ↓
COMPLETED
```

#### 예외 상태

- `RETRYING`: 통신 응답이 없어 재전송 중
- `FAILED`: 일정 횟수 이상 실패
- `CANCELLED`: 사용자가 목적지를 변경하거나 하차함

#### 왜 필요한가?

버튼을 누른 사실과 하차벨이 실제로 작동한 사실은 다르다. 요청 ID와 상태를 관리해야 중복 작동, 유실, 오래된 요청 실행을 막을 수 있다.

#### 임팩트 있는 문장

> 이벤트를 보내는 것보다, 이벤트가 어디까지 처리됐는지를 추적하는 것이 시스템의 신뢰성을 결정한다.

---

### Slide 9. 구현 결과를 증거로 보여주기

#### 목적

“만들 수 있다”가 아니라 “검증했다”를 보여준다.

#### 넣을 자료

- 실제 앱 또는 웹 화면 캡처
- Roblox 시뮬레이션 영상의 핵심 장면
- Firebase 데이터가 변하는 화면
- Pico 2W 또는 하차벨 회로 사진
- 요청 생성부터 작동까지의 로그

#### 검증 시나리오

| 테스트 | 기대 결과 |
|---|---|
| 목적지 선택 | 예약 상태가 생성됨 |
| 목적지 접근 | 하차 알림 발생 |
| 하차 요청 | 요청 ID가 생성됨 |
| 장치 수신 | 상태가 DELIVERED로 변경됨 |
| 벨 작동 | 상태가 ACTUATED 또는 COMPLETED로 변경됨 |
| 중복 클릭 | 같은 요청이 두 번 작동하지 않음 |

가능하다면 성공 횟수, 평균 응답 시간, 통신 실패 시 복구 여부를 실제 측정해 제시한다.

### Slide 10. 기술 선택의 이유

#### 목적

라이브러리 이름 나열을 피하고 선택 근거를 보여준다.

#### 구성 예시

| 기술 | 선택 이유 |
|---|---|
| Roblox Studio / Lua | 이동·정류장·상태 로직을 빠르게 시뮬레이션 가능 |
| Firebase SDK | 인증과 실시간 상태 공유를 짧은 코드로 구현 가능 |
| WebSocket | 서버 이벤트를 지연 없이 전달하기 적합 |
| MQTT | Pico 2W 같은 장치에 작은 명령을 전달하기 적합 |
| MicroPython | 하드웨어 제어 로직을 빠르게 수정하고 검증 가능 |
| REST API | 노선·정류장 데이터 조회에 구조적이고 이해하기 쉬움 |

#### 주의

실제로 사용하지 않은 라이브러리는 “사용 기술”이 아니라 “실제 서비스 확장 시 고려할 기술”로 표시한다.

### Slide 11. 한계와 안전 설계

#### 목적

약점을 숨기지 않고, 해결 계획까지 제시한다.

#### 한계

- GPS 오차: 터널·실내·고층 건물 주변에서 위치가 흔들릴 수 있음
- 네트워크 장애: 요청 전달이 늦거나 실패할 수 있음
- 탑승 판별: 사용자가 어떤 버스에 탔는지 자동으로 확정하기 어려움
- 실제 차량 연결: 차량 전기 시스템과 안전 규격 검토 필요
- 개인정보: 이동 위치를 최소한으로 수집하고 보관 기간을 제한해야 함

#### 대응 방향

- GPS와 정류장 이벤트를 함께 사용
- 통신 실패 시 로컬 알림 제공
- 요청 재전송과 타임아웃 적용
- 고유 요청 ID로 중복 실행 방지
- 실제 하드웨어와 차량 회로를 전기적으로 분리

#### 발표 효과

완벽하다고 주장하는 것보다, 실패 가능성을 예상하고 설계에 반영했다는 점이 더 전문적으로 보인다.

---

### Slide 12. 결론: 기능이 아니라 가치로 마무리

#### 화면용 문구

버마티는 하차벨을 대신 누르는 도구에 그치지 않는다.

사용자 입력, 위치 정보, 대중교통 데이터, 실시간 통신, 하드웨어 제어를 연결해 대중교통 이용의 행동 부담을 줄이는 시스템이다.

#### 마지막 세 문장

1. 문제: 하차 과정에는 상황에 따라 행동 부담과 불안이 생긴다.
2. 해결: 버마티는 위치와 운행 상태를 이용해 하차 시점을 보조한다.
3. 가능성: 프로토타입에서 검증한 구조를 실제 교통 데이터와 안전한 장치 인터페이스로 확장할 수 있다.

## 4. 네컷 만화 구성 조언

네컷 만화는 기술을 설명하는 공간이 아니라, 문제와 해결을 기억하게 하는 공간으로 사용한다.

### 권장 장면

1. 혼잡한 버스에서 하차벨에 손이 닿지 않는 상황
2. 앱에서 목적지 정류장을 선택하는 장면
3. 위치와 버스 경로를 계산해 하차 시점을 알려주는 장면
4. 하차벨 요청이 전달되고 사용자가 안심하는 장면

### 말풍선 원칙

- 한 칸에 한 문장
- 12~18자 내외
- 전문 용어는 말풍선보다 하단 캡션에 배치
- 화면 안에 작은 글자를 많이 넣지 않음

### 추천 캡션

`불편함 발견 → 목적지 설정 → 위치 기반 판단 → 하차 요청 전달`

## 5. 디자인 원칙

색상은 기능의 상태를 구분하는 데 사용한다.

- 파랑: 데이터·통신
- 초록: 정상 처리·완료
- 빨강: 오류·주의

### 글자량

슬라이드 본문은 발표자가 읽는 대본이 아니다. 한 화면에 긴 문단을 넣지 말고, 자세한 설명은 발표자 노트 또는 별도 질문 대비 자료에 둔다.

## 6. 심사위원 질문 대비 핵심 답변

### Q. 단순한 하차 알림 앱과 무엇이 다른가?

버마티는 알림만 제공하는 것이 아니라, 목적지·위치·버스 상태를 연결하고 하차 요청을 처리하는 상태 기반 시스템을 목표로 한다.

### Q. GPS가 틀리면 어떻게 하는가?

GPS 단독 판단을 피하고 버스 위치, 이동 방향, 정류장 이벤트, 사용자 확인을 함께 사용한다. 통신이 불안정할 때는 마지막 상태를 기반으로 로컬 알림을 제공한다.

### Q. 실제 버스에 바로 적용할 수 있는가?

현재 프로토타입과 실제 차량 적용은 구분해야 한다. 실제 적용에는 교통 데이터 연동, 운수회사 협의, 차량 회로 안전성 검토, 인증과 장애 대응 시험이 필요하다.

### Q. 가장 어려운 기술 문제는 무엇인가?

하차벨을 한 번 작동시키는 것보다, 어떤 버스의 어떤 요청인지 식별하고, 요청이 실제로 처리됐는지 확인하며, 통신 실패와 중복 실행을 제어하는 것이 더 어렵다.
